# Nodes

Every graph node, filterable by category or capability. Each card is
a technical datasheet: what it consumes, what it produces, which
policies apply, and which file owns the implementation.

Five categories map to distinct responsibilities:

- **Safety** — runs before any other branch and cannot be bypassed by
  response style, therapeutic approach, or memory mode (`crisis_gate`,
  `crisis_resource_lookup`, `crisis_response`, `crisis_log`)
- **Routing** — non-therapeutic branches that short-circuit the
  pipeline (`memory_control_gate`, `memory_control`,
  `grounded_lookup_gate`, `grounded_answer`, `therapeutic_subgraph`)
- **Memory** — retrieval and structured working context
  (`load_memory`)
- **Extraction** — post-response LLM side effects that run in parallel
  (`extract_facts`, `extract_procedural`)
- **Terminal** — transcript finalization, pure state manipulation
  (`finalize_turn`)

## Branch ordering

The parent graph is intentionally a fixed sequence of gates rather
than a single LLM router. After the crisis gate, the therapeutic
branch passes through two operational gates before any memory is
loaded:

```text
crisis_gate
  ├─ (crisis)        crisis_resource_lookup → crisis_response → crisis_log
  └─ memory_control_gate
       ├─ (command)  memory_control                  ← skips memory + therapeutic
       └─ grounded_lookup_gate
            ├─ (lookup) grounded_answer              ← skips memory + therapeutic
            └─ load_memory → therapeutic_subgraph
```

All five "non-therapeutic" branches converge at `finalize_turn_node`,
which always runs and emits the assistant turn into `history` and
`transcript` via the `operator.add` reducer.

## Adding a new node

When you add a node to the graph, think through three things:

**Does it do I/O?** If yes, register it with `retry_policy=RetryPolicy(max_attempts=2)` in `build_agent_workflow`. The retry policy is defense-in-depth for transient failures that escape the node's own error handling.

**Does it write to a shared state field?** If multiple nodes write to the same field (like `diagnostics`, `session_progress`, or `exercise_state`), the field needs a reducer (`_merge_dicts` for dicts, `operator.add` for lists) in `AgentState`. Without a reducer, nodes will clobber each other's writes.

**Can it run in parallel?** If the node has no ordering dependency with its siblings (the way the two extractors don't), wire it as a fan-out edge from its parent. The reducers handle concurrent writes safely.

**Is it a gate or a worker?** Gates return `Command(goto=...)` to short-circuit the pipeline; workers return a state delta and rely on a static edge. Use a gate when the decision is binary and adds latency on every turn even when the branch isn't taken (e.g., the memory-control gate avoids running `load_memory` on slash-command turns).
