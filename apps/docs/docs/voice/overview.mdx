# Voice (LiveKit)

OpenCouch's voice runtime is a **LiveKit-native agent worker** that
runs alongside the FastAPI backend. The browser joins a LiveKit
room over WebRTC; LiveKit handles audio transport and dispatches
the `opencouch-voice` agent into the room when the participant
joins. The worker owns session setup, agent handoffs, tasks, and
shutdown persistence.

:::warning Voice is a separate runtime
The voice path is its own surface — it does **not** run the
LangGraph text agent live on every spoken turn. Memory is loaded
into the prompt at session start, refreshed selectively
mid-session via semantic retrieval, and persisted via the shared
session-end seam on disconnect. The LangGraph crisis gate is not
in the voice hot path; voice has its own deterministic crisis
safety net plus a model-invoked `crisis_check` tool that applies
the deterministic crisis policy.
:::

## Two lifetimes

There are two distinct lifetimes inside this package — keeping
them separate is the key to understanding what's reusable across
sessions and what isn't.

| Lifetime | Lives in | What it owns |
|---|---|---|
| **Worker process** | `voice/livekit/agent.py` | One shared `PersistentAgentRuntime` (lazy-init), the configured memory store, the optional control LLM client. Survives across LiveKit jobs. |
| **Session (one room)** | `AgentSession[SessionData]` | One room conversation. The typed `SessionData` carries `user_id`, `thread_id`, `memory_mode`, `crisis_level` / `max_crisis_level`, `proactive_recall_enabled`, `pending_memory_delete`, `therapeutic_instructions`, `injected_semantic_memory_keys`, `recent_exercise_types`. Lives in memory; anything that must persist goes through the runtime. |

## Room routing

There are two ways to get the agent into a room.

### Token-dispatch flow (production / browser path)

1. Client calls `POST /api/voice/livekit/token`.
2. `voice/livekit/api.py` mints a participant JWT for a room
   and embeds `RoomAgentDispatch(agent_name="opencouch-voice")`
   when `dispatch_agent=True`.
3. The browser joins the room with that token. LiveKit dispatches
   the named agent automatically.
4. `@server.rtc_session(agent_name="opencouch-voice")` in
   `agent.py` fires; `opencouch_voice()` connects, reads
   `user_id` / `thread_id` from job or participant metadata,
   loads memory, and starts the session.

This is the mode for `uv run python -m voice.livekit.agent start`.

### Direct-connect flow (manual testing)

1. Run `uv run python -m voice.livekit.agent connect --room <name>`.
2. The agent joins the named room directly as a participant.
3. A browser or other client joins the same room separately.

Use `dispatch=0` on the test page when running this way — otherwise
the room ends up with both a directly-connected agent **and** a
token-dispatched one. The local test page exposes a dispatch toggle.

## In-session routing

There is no separate router graph at session time. Routing is
done with **LiveKit agent handoffs** and **bounded tasks**.

```text
TherapeuticAgent  (default session agent)
  → GroundingTask     when start_grounding_exercise() is called
  → CrisisAgent       when crisis_check() escalates
                      OR the deterministic safety net fires

CrisisAgent
  → TherapeuticAgent  when de_escalate() is called
                      (instructions restored from
                       SessionData.therapeutic_instructions)
```

### TherapeuticAgent

The default session agent. Responsibilities:

- greet the user on session start (`on_enter()` adds a brief opening nudge)
- hold the main therapeutic conversation
- run `on_user_turn_completed()` after each user turn — this hook does **two deterministic things**:
  - **crisis safety net**: `matches_crisis_keywords()` can force an immediate `session.update_agent(CrisisAgent(...))` without waiting for the model
  - **mid-session semantic retrieval**: when `proactive_recall_enabled` is on, the latest user turn drives a small semantic search; new facts (deduped via `injected_semantic_memory_keys`) are pushed into chat context with `update_chat_ctx()`
- expose memory-control tools (show / status / toggle recall / two-turn deletion confirm)
- expose `save_insight()` for durable semantic writes
- expose `answer_grounded_factual_lookup()` for explicit factual lookups
- expose `start_grounding_exercise()` to enter a `GroundingTask`

### GroundingTask

A bounded `AgentTask` for voice-friendly exercises. It is **not** an
alternate full agent — it owns the interaction only until the user
completes or exits one exercise.

Properties:

- built from the existing exercise registry in `agent/therapeutic/guided_exercise.py`
- inherits conversational context, but **not** prior instructions or tool-call traces (handoffs intentionally drop those to avoid leakage)
- `complete_step()` advances; `exit_exercise()` stops early
- completion returns an `ExerciseResult` to the parent agent

**Voice allowlist.** The text-mode exercise registry has 13
exercises; voice exposes 10 of them — visually-loaded imagery
exercises (`defusion_leaves_on_stream`,
`thought_work_simple_record`,
`thought_work_behavioral_experiment`) are excluded so spoken users
don't have to read or hold detailed visual scenes.

| Voice-allowlisted exercise types |
|---|
| `grounding_5_4_3_2_1`, `grounding_box_breathing`, `grounding_stop_technique`, `grounding_muscle_relaxation` |
| `behavioral_activation_tiny_action`, `self_compassion_break` |
| `emotion_regulation_improve`, `emotion_regulation_gratitude` |
| `defusion_values_compass`, `thought_work_continuum` |

Generic requests ("help me calm down") rotate away from
`recent_exercise_types` so the same exercise doesn't repeat;
explicit requests ("do box breathing again") are honored as-is.

**Spoken vs. typed turns.** The session tracks whether the latest
turn was spoken or typed in the room — typed turns can pick from
the broader registry, spoken turns stay on the voice-safe subset.

### CrisisAgent

Narrow handoff target. Entered from either the LLM-driven
`crisis_check()` tool or the deterministic keyword safety net. Its
priorities are intentionally tighter than the main agent:

- acknowledge risk
- expose `provide_crisis_resources()` — same verified-hotline
  lookup the LangGraph text agent uses, with two extra rules: only
  trusts a user-stated location, never infers from IP / timezone /
  accent / someone else's location
- stay present; avoid normal therapeutic exploration
- `de_escalate()` returns control to a fresh `TherapeuticAgent`
  using the original instructions captured in
  `SessionData.therapeutic_instructions`

`crisis_level` can drop back to 0 after de-escalation, but
`max_crisis_level` is preserved through the session for shutdown
persistence and downstream analysis.

## Prompting

Three layers, in order of stability:

| Layer | Source | When it loads |
|---|---|---|
| **Base therapeutic prompt** | `voice.realtime.build_voice_system_prompt()` | Session start. Captured in `SessionData.therapeutic_instructions` so it can be restored after crisis de-escalation. Compact by design — Realtime sessions have a tighter instruction budget than the LangGraph stack. |
| **Situational nudge** | `Agent.on_enter()` per agent | Each handoff. `TherapeuticAgent` adds a brief opening greeting; `CrisisAgent` adds a brief crisis-response instruction. |
| **Task-scoped exercise prompt** | `GroundingTask` | When entering an exercise. Includes the full step plan, pacing rules, completion criteria, and exit behavior. Tells the model to deliver exactly one step at a time. |

The base prompt assembles short, voice-shaped versions of:

- core identity and response style
- safety boundaries
- procedural memory ("User preferences")
- semantic memory ("Known context about the user")
- episodic memory ("Relevant prior sessions")

## Memory in three phases

| Phase | When | What runs |
|---|---|---|
| **Startup load** | `opencouch_voice()` boots the session | Compact memory load when `memory_mode` is persistent — semantic facts, episodic arcs, procedural rules, the recall toggle — all flow into `build_voice_system_prompt()` |
| **Mid-session retrieval** | `TherapeuticAgent.on_user_turn_completed()` | When `proactive_recall_enabled`, a small semantic search keyed off the latest user text. Already-injected facts are skipped via `SessionData.injected_semantic_memory_keys`. New facts are pushed in as a system message via `update_chat_ctx()`. Handoffs carry **only conversational context**, not prior instructions or tool-call artifacts. |
| **Session-end persistence** | Shutdown hook | `session.history` is serialized into a transcript of user/assistant messages and handed to `runtime.end_transcript_session(...)`. Both `crisis_level` and `max_crisis_level` are passed through so downstream extraction sees peak severity. |

## Tools

All tools are LiveKit `@function_tool()` declarations. They share
`SessionData` via the `RunContext`.

| Tool | Owner | Purpose |
|---|---|---|
| `save_insight` | TherapeuticAgent | Writes a concise semantic fact under the session `user_id` namespace. Tagged with `thread_id` + `created_at`. Calls `disallow_interruptions()` first so a barge-in can't hide a durable mutation. |
| `show_saved_memory` | TherapeuticAgent | Lists saved facts, session summaries, and style preferences. |
| `show_memory_status` | TherapeuticAgent | Reports counts and the proactive-recall state. |
| `set_proactive_memory_recall` | TherapeuticAgent | Toggles proactive recall. |
| `prepare_memory_deletion` / `prepare_indexed_memory_deletion` / `select_memory_deletion_candidate` | TherapeuticAgent | Selects a saved memory but does not delete it. |
| `confirm_memory_deletion` | TherapeuticAgent | Deletes the selected memory only after explicit confirmation; `disallow_interruptions()` is called first. |
| `cancel_memory_deletion` | TherapeuticAgent | Clears the pending deletion. |
| `start_grounding_exercise` | TherapeuticAgent | Enters `GroundingTask` for a voice-allowlisted exercise. |
| `answer_grounded_factual_lookup` | TherapeuticAgent | Explicit factual lookup using the shared search-grounded backend helper. Says "I can't verify that" when no search-capable LLM is configured rather than guessing. |
| `crisis_check` | TherapeuticAgent | Model-invoked deterministic escalation check. Level 3 → `CrisisAgent`; level 2 → `CrisisAgent`; level 1 → ask to clarify; level 0 → continue. |
| `provide_crisis_resources` | CrisisAgent | Verified local hotlines via the same lookup the text agent uses. Asks for location if not stated; never infers from IP / timezone / accent. Falls back to emergency / 988 guidance when search fails. |
| `de_escalate` | CrisisAgent | Hands control back to a fresh `TherapeuticAgent` with `therapeutic_instructions` restored. |

## Startup modes

`agent.py` ends with `agents.cli.run_app(server)`, so the standard
LiveKit Agents CLI is available:

| Command | What it does |
|---|---|
| `uv run python -m voice.livekit.agent dev` | Local development mode — works with the LiveKit Agent Console |
| `uv run python -m voice.livekit.agent start` | Long-running worker for token-dispatch flows |
| `uv run python -m voice.livekit.agent connect --room <name>` | Direct room join for manual testing |
| `uv run python -m voice.livekit.agent console` | Local console session — no LiveKit room |
| `uv run python -m voice.livekit.agent console --text` | Text-only console for prompt / tool smoke tests |
| `uv run python -m voice.livekit.agent download-files` | Pre-download model assets (use before first `start` if cold-starts time out) |

## Common failure modes

| Symptom | What to check |
|---|---|
| Agent joins a room but nothing happens | The session waits for a non-agent participant before starting. Verify the browser actually joined the same room name. Watch for `livekit session: starting user=…` in the logs. |
| Two agents in one room | You combined `connect --room` with `dispatch=1`. Use `dispatch=0` on the test page when direct-connecting. |
| First worker subprocess times out on cold start | Run `download-files` first, then prefer `start` for long-running worker testing. |
| Browser loads but token creation fails | Missing `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET`. The token endpoint returns 503. |
| Console works, browser doesn't | `console` mode skips LiveKit entirely. Use `start` + token-dispatch (or `connect --room`) to validate room dispatch and media flow. |
| Same grounding exercise keeps repeating | Generic requests rotate away from `recent_exercise_types`; explicit repeat requests are honored. If repetition still feels excessive, the likely problem is overuse of `start_grounding_exercise()` for cases that should have stayed conversational. |
| Crisis routing feels abrupt or sticky | The deterministic safety net can force a handoff without the model's input. `crisis_level` returns to 0 after `de_escalate()`, but `max_crisis_level` is preserved by design. Look for `safety net: crisis keywords detected` and `CrisisAgent: de-escalating back to TherapeuticAgent`. |
| Memory missing or inconsistent | Startup load vs. mid-session retrieval are separate paths. Check `OPENCOUCH_MEMORY_MODE`, the per-session override sources (token / participant metadata), and the `memory loaded facts=…` / `injected semantic memory facts=…` log lines. |

## Text vs voice

| Concern | Text mode | Voice mode |
|---|---|---|
| **Runtime** | LangGraph `StateGraph` per turn | LiveKit `AgentSession` per room |
| **Routing** | crisis_gate → operational gates → therapeutic subgraph | Agent handoffs (`TherapeuticAgent` ↔ `CrisisAgent`) + bounded tasks (`GroundingTask`) |
| **Prompt** | Full layered assembly per turn | One bounded base prompt at session start + per-handoff nudges + per-task instructions |
| **Tools** | `find_local_crisis_resources`, `answer_grounded_lookup` (node-invoked) | `@function_tool` declarations on each agent — model decides when to call |
| **Crisis** | Graph-level `crisis_gate_node` first, before anything | `crisis_check()` tool + deterministic keyword safety net + `CrisisAgent` handoff |
| **Memory** | Read + write through normal chat lifecycle | 3-phase: startup load → mid-session selective retrieval → shutdown transcript replay |
| **Exercises** | All 13 in the registry | Voice allowlist of 10 (excludes visually-loaded ones) |
| **UI maturity** | Primary, stable | Active development, narrower than text |
