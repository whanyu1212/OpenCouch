# Why a Runtime Topology, Not a ReAct Loop

OpenCouch uses an **app-owned runtime topology** around the OpenAI Agents
SDK runner instead of a ReAct-style agent loop. This isn't a framework
preference — it's a safety and correctness decision driven by the domain.

---

## The core difference

| | ReAct loop | Runtime topology |
|---|---|---|
| **Execution order** | LLM *chooses* what runs next | Topology *enforces* what runs next |
| **Safety guarantee** | Prompt says "check safety first" | Runtime makes it impossible to skip |
| **Tool usage** | LLM decides when/if to call tools | Runtime branches invoke tools at fixed lifecycle points |
| **Extraction** | Optional step the LLM might skip | Runtime side effect — always runs after response |
| **Enforcement** | Runtime guideline (can drift) | Compile-time invariant (cannot drift) |

A ReAct loop is a programming pattern where an LLM picks actions.
Those choices can be shaped by prompting, but they aren't
*architecturally guaranteed*. OpenCouch keeps ordering in application code:
crisis classification, safe-turn triage, retrieval, SDK specialist execution,
finalization, and side effects are explicit runtime steps rather than actions
the model is allowed to reorder.

---

## Why this matters for mental health

In a support agent, two failure classes are unacceptable:

1. **Skipped safety check** — a user in crisis gets a therapeutic
   response instead of crisis routing and resources
2. **Corrupted memory** — extraction runs before the response exists,
   or doesn't run at all, breaking cross-session continuity

Both failures are *possible* in a ReAct loop through prompt drift,
model updates, cost-optimization shortcuts, or adversarial input.
Both are prevented by the runtime topology because there is no serving path
that reaches ordinary response generation before the crisis gate, and
post-response side effects are scheduled by the runtime rather than by the
model.

---

## Structural guarantees

### 1. Safety always runs first

```text
message → crisis_gate → crisis branch | safe-turn triage
```

Every message enters the runtime through the crisis gate. The gate writes
the crisis assessment and routes to either crisis response handling or
safe-turn triage.

**In a ReAct loop**, the LLM could decide to load memory first, or
skip directly to response generation. Prompt hardening reduces this
risk but cannot eliminate it — especially under adversarial input or
model version changes.

### 2. The response path finishes before side effects

```text
SDK response → turn finalization → persistence → post-response side effects
```

The response must be finalized (appended to transcript) before the runtime
persists the turn. Long-term memory writes are explicit tool or session-end
operations, not automatic cleanup after every response.

**In a ReAct loop**, persistence and other cleanup side effects can
be skipped for latency or run before the response is complete.

### 3. Tool invocation is positional, not emergent

The web search for crisis resources is called from the crisis branch, and
factual lookup is called from the grounded-lookup branch. Both are fixed
runtime branches chosen by typed routing, not emergent ReAct tool calls that
can be hallucinated, omitted, or sequenced incorrectly.

```python
# Inside the crisis-resource branch - always runs before crisis response
location, resources, status = await find_crisis_resources(state, llm_client=llm_client)
```

**In a ReAct loop**, the LLM generates
`{"tool": "web_search", ...}` as text, which gets parsed. The agent
might hallucinate a tool, forget to call it, or call it at the wrong
time.

### 4. Routing is paired with state updates

The crisis gate and safe-turn triage each return a state delta alongside
the route decision. The runtime applies those deltas before selecting the
next branch:

```python
apply_state_delta(state, routing_delta)
```

**In a ReAct loop**, routing and state updates are separate steps —
the LLM outputs an action string, it gets parsed, then state is
updated. Parsing failures, malformed JSON, or partial writes can
leave state inconsistent.

### 5. Transcript continuity via reducers

State fields like `history` and `transcript` use `operator.add`
reducers. When turn finalization returns `{"transcript": [assistant_turn]}`,
the reducer appends it to the checkpointed prior turns automatically.

**In a ReAct loop**, manual `state["transcript"].append(...)` calls
are error-prone across checkpoint/restore cycles — duplicate turns,
missing history, ordering bugs.

## What a ReAct loop would look like here

```python
# Pseudocode — the ReAct alternative
while True:
    action = llm.decide_next_action(state)  # LLM chooses

    if action == "check_crisis":
        assessment = check_crisis(state)
    elif action == "load_memory":
        # BUG: agent skipped crisis check
        memory = load_memory(state)
    elif action == "respond":
        # BUG: agent responded without safety or memory
        response = generate_response(state)
    elif action == "persist_state":
        # BUG: agent might never reach this
        persist_turn(state)
```

Every `elif` branch is a potential skip. The LLM *should* follow the
right order, but "should" is not "must."

---

## When a ReAct loop is better

ReAct loops excel when:

- The task is open-ended and the agent needs to explore
- Tool sequences are unpredictable and context-dependent
- The cost of a wrong action is low (web browsing, code search)
- Autonomy and creativity matter more than determinism

OpenCouch's pipeline is the opposite: the sequence is known, safety
ordering is critical, and the cost of a wrong action (missed crisis)
is high. The runtime encodes these constraints once and enforces them
regardless of prompt changes, model updates, or adversarial inputs.
